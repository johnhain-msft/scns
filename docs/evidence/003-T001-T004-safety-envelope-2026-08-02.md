## T001 — isolated verification environment (quickstart §0a)

`SCNS_HOME` alone does **not** scope the scheduler DB, so `BROKER_DB_PATH` is exported alongside it.

```
T001 SCNS_HOME=/var/folders/tv/w7m7yb7j57lchccf9s9yjktc0000gn/T/tmp.IOlEqXVIlR
T001 BROKER_DB_PATH=/var/folders/tv/w7m7yb7j57lchccf9s9yjktc0000gn/T/tmp.IOlEqXVIlR/broker.db
T001 envelope file=/tmp/scns-003-envelope.sh
```

**Deviation from the task text, and why.** The task says `export SCNS_HOME=$(mktemp -d)`. An `export` dies
with the shell that ran it, and each automated step here runs in a **fresh process** — so a literal export
would leave every later task (T003, T006, T007) silently pointing at the *real* `~/.scns`, which is the exact
failure FR-035 exists to prevent. The envelope is therefore also written to a sourceable file:

```bash
source /tmp/scns-003-envelope.sh   # re-establishes SCNS_HOME + BROKER_DB_PATH in any later shell
```

`/tmp/scns-003-envelope.sh` contains only the two exports. Every subsequent step in this write-up sourced it
rather than re-deriving the path.

**Write-traffic constraints honoured**: no write traffic targeted `~/.scns/memory/experience.db`; no
`POST /api/extension/context` was issued (it appends a row despite looking like a read); broker `:3456` was
not contacted at all.

### Does the sidecar actually change the answer? — re-measured, both ways

A main-file-only control copy was made alongside it (`$SCNS_HOME/mainonly/experience.db`) and both were read
through `{ readonly: true, fileMustExist: true }` handles using the shipped arm-sample predicates
(`retriever != 'full' AND explore_arm IS NOT NULL AND prompt_origin IS NOT 'machine'`, plus
`human_outcome IS NOT NULL` on the settled side):

```
[with-sidecars]
  total rows      : 2068
  served by arm   : hybrid=73 magma=318 multihop-iter=86
  settled by arm  : magma=20 multihop-iter=7
[main-file-only]
  total rows      : 2056
  served by arm   : hybrid=73 magma=313 multihop-iter=84
  settled by arm  : magma=18 multihop-iter=7
```

**Verdict: the sidecar is load-bearing and the copy is WAL-inclusive.** 12 rows (2068 − 2056) exist only in
the WAL, and 2 of them are settled `magma` rows (**20 vs 18**).

**Honest correction to the standing claim — and a correction to how I first reported it.**

`quickstart.md` §0b states the WAL is decisive for the *challenger*: `magma 23 / multihop-iter 5` without it
vs `26 / 7` with it. **Those §0b figures are on the OLD keying** (`COALESCE(explore_arm, retriever)`) — proved
by `quickstart.md:159`, which reads "under both old (26/7) and new (17/7) counts." My first pass compared that
`26` against today's corrected `20` and attributed the drop to the checkpoint. **That was wrong and is
retracted:** settled rows only accrue, so a checkpoint cannot lower a count. The `26 → 20` gap is almost
entirely the **keying fix** (`a21108d`, C2), not the WAL and not a checkpoint.

Re-measured today on both copies, both keyings, so the comparison is like-for-like:

| copy | old `COALESCE(explore_arm, retriever)` | corrected (`explore_arm` alone) |
|---|---|---|
| with-sidecars (WAL-inclusive) | `magma=29 multihop-iter=7` | `magma=20 multihop-iter=7` |
| main-file-only (control) | `magma=27 multihop-iter=7` | `magma=18 multihop-iter=7` |

`excluded.unassigned = 9` on both copies, and the partition reconciles exactly: `20 + 9 = 29`, `18 + 9 = 27`.
Accrual is monotonic on **both** keyings against 2026-08-01 (old `26 → 29`; corrected `17 → 20`; main-only old
`23 → 27`), which is the expected direction and confirms nothing was lost.

**The conclusion survives the re-attribution.** `multihop-iter` settles at **7 in all four cells**, so the WAL
no longer moves the challenger — whereas on 2026-08-01 it did (`5` main-only vs `7` WAL-inclusive). The general
rule ("copy the sidecars or you read a stale snapshot") holds and is re-confirmed on the *incumbent* (`magma`
18 → 20 corrected, 27 → 29 old). The specific "decisive at the challenger's `minN` boundary" instance does
**not** reproduce today. Anything downstream depending on the challenger count being WAL-sensitive should
re-derive it.

> **Stale docstrings flagged for T007.** `src/memory/experience-store.ts:560-561` and
> `test/unit/memory/arm-sample.test.ts:10-11` cite "magma 27 / multihop-iter 7" vs "magma 18 / multihop-iter 7".
> Those are today's **main-file-only** figures; the WAL-inclusive pair is **29 / 20**. The numbers are not wrong,
> but they are unlabelled as to which copy they came from. T007 should label them rather than silently inherit them.

### Incidental finding — the documented glob is wider than it reads

`cp ~/.scns/memory/experience.db*` also matched **8 unrelated stale backups** (~28 MB):
`experience.db.bak-2026-07-25T02-07-24-084Z`, `…-2026-07-25T02-07-58-404Z`, `…-20260727-131242`,
`…bak-qc-2026-07-25T02-55-13Z`, `experience.db.bak.1785453679` (+ its own `-wal`/`-shm`), and
`experience.db.bak.cleanup.1785540850`. Harmless here (they land inside the isolated dir and nothing reads
them), but a later step that globs `$SCNS_HOME/.scns/memory/*.db*` would pick up month-old corpora. Prefer
an explicit three-file copy (`experience.db`, `-wal`, `-shm`) over the bare `*`.

All three rows were byte-identical. **Do not read that as a strength claim.** The guard bracketed

under normal broker activity. What the guard does establish is the narrow, honest thing: **across the cp and
the probe, the live corpus did not move.** The guard is not vacuous — the broker was live throughout
(`memory-reindex` `run_count=4134`) — but it is 80 seconds of evidence, not a session-wide isolation proof.

Against the quickstart's three-claim standard:

1. **`experience.db` main-file `mtime` + `size` identical before and after** — yes:
   `mtime=1785681351 size=7053312` on both sides.
2. **Every handle opened on the live path was `{ readonly: true, fileMustExist: true }`** — yes. The only

3. **No write-path probe was issued** — yes. No `POST /api/extension/context`; no broker contact.

The WAL did not move during this session, which is luck rather than proof — a moving `-wal` would have been
the running broker's own traffic and MUST NOT be reported as a guard failure.

## Post-review remediation — stale broker vs. the Monday F1 deadline

Raised by an adversarial review of this branch, independently re-verified, and **user-approved** before any
action on the live broker (`:3456` is human-owned).

**The defect.** The F1 fix (`858257d`, "emit the Monday verdict from the cron path") was committed and built
into `dist/` at `14:52:20`, but the running broker had started at ~`10:40` — it was serving pre-F1 code. The
proof was an orphan: `dist/memory/similar-episode.js` (mtime `12:23`) whose *source* was deleted in `2f251b0`
— `tsc` does not remove stale outputs, so its presence alongside a `14:52` `cli.js` established that a rebuild
post-dated the broker's start. The cron fires `0 9 * * 1` = **2026-08-03 09:00**, so an un-restarted broker
would have run the old path on the deadline.

**Two parts of the report did not survive checking, and are recorded as corrections:**
- `~/.scns/reviews/` being absent is **not** a defect — `src/suggest/weekly-report.ts:297` calls
  `mkdirSync(join(scnsDir,'reviews'), { recursive: true })` and creates it on first use (proved below).
- The broker would **not** have stayed stale indefinitely — `com.scns.daily-restart` fires at `06:00` daily,
  three hours before the Monday cron.

**Remediation.** Restarted via the sanctioned blue/green script, not a blind kill:

```
$ scripts/broker-restart.sh
… canary healthy → drain (0 active) → 0 agents snapshotted → kickstart → fresh broker healthy ✓
RESTART_EXIT=0
```

**Live-confirmed post-state:**


Broker start (`15:43:24`) now post-dates the build (`14:52:20`), so the F1 code is the code being served.

`~/.session-broker/data.db`, *not* `~/.scns/broker.db`, which has no `scheduled_tasks` table):

**Restart did not introduce errors.** `~/.scns/logs/broker_error.log` has mtime `15:17:16` — *before* the

is `unavailable` by design on a freshly started broker.

prove the Monday run will produce a good verdict — that depends on T006's red-state reproduction, which has
