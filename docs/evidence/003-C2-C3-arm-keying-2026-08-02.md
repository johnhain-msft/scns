denominator must share the numerator's population or the funnel is meaningless, so this is the
correction working as intended — but a reader of Monday's report will see magma's served count fall
5× with no explanation unless the report says why. Called out here so it is not read as data loss.

**Nine never-assigned rows were being credited to the incumbent — inflating `magma`'s sample by 50%
against the very challenger it was being compared with (27 vs 7 → 18 vs 7).**

Two properties now hold that could not be checked before:
- `countSettledByArm` + `countExcludedFromArmSample` **partition** the settled non-`full` rows exactly

  rows; FR-027c makes it countable.
- `loadRewardRows` returns 25 = 18+7 — the learner's verdict and the weekly report are provably
  computed over the identical population (SC-003). This is asserted as a test, not just measured here.

Corpus was 2056 rows at the earlier C6 measurement, 2057 at this one, and 2058 when the judge
re-measured ~20 minutes later: the live system is in use throughout. Every figure above is a read of a

**M2 survived because `ARM_SAMPLE_WHERE` guarantees `explore_arm IS NOT NULL`, making the `??` branch
unreachable.** Unreachable is not absent — it is one loosened predicate away from returning, which is
exactly how the original defect survived its gate. The behavioural suite could not distinguish it, so
two guards were added that bind the *invariant* rather than the symptom:
1. a source-structural guard (walks `src/`, strips comments, zero fallback keyings);
2. a coupling invariant — `loadRewardRows`'s arm histogram must equal `countSettledByArm` exactly.
M5 proves guard 2 is live: loosening the learner's predicate now fails 3 tests.

Had I stopped at the first green, C2 would have been reported fixed with an untested learner.

## 7. Why C2 survived: the defect was ASSERTED, not merely untested

Running the full unit suite after the fix turned up **two pre-existing tests that encoded the fallback
keying as intended behaviour**. This is the actual root cause of C2's longevity, and it is a stronger
finding than the original analysis: a correct fix made the suite go red, so the fix looked like the
regression.

| Test | Asserted | Meaning |
|---|---|---|
| `test/unit/memory/briefing-exploration.test.ts:202` — *"countSettledByArm keys on the FINE arm (explore_arm) **and falls back to the retriever family**"* | `expect(byArm.get('magma')).toBe(2)` with the comment `// the explored incumbent row + the legacy magma-family row` | The 50% inflation, written down as the requirement |
| `test/unit/reward/kto-learner.test.ts:95` — *"loads settled rows with arm **(explore_arm ?? retriever)**"* | `expect(byQ['hybrid']).toMatchObject(...)` for a row logged `levers: {}` | A never-assigned row laundered into an arm named after the default retriever family |

Both were rewritten to assert the corrected behaviour, keeping their original coverage (propensity
from `flag_state`, unsettled-row exclusion) and carrying a `HISTORY` comment so the next reader learns
why the assertion flipped rather than assuming a mistake.

Full unit suite before this correction: `Tests 1 failed | 6817 passed | 1 skipped (6819)`
(the single failure was the second table row above). After: both files green —
`briefing-exploration.test.ts` `Tests 13 passed (13)`, `kto-learner.test.ts` `Tests 15 passed (15)`.

Note the baseline flake (T005: `Tests 1 failed | 6763 passed`, a parallel-worker race in an unrelated
file) did NOT recur in this run — so the one failure here was genuinely attributable to this change,
which is exactly what the T005 baseline exists to establish.

**Implication for the review:** "all tests pass" was true before this feature AND the arm comparison
was wrong. The suite was measuring agreement with itself. That is the same failure mode as the
`grep "COALESCE(explore_arm"` gate in §1 — a check shaped so it cannot fail.
