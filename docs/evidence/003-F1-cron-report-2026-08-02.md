## The defect

`weekly-promotion-review` (`src/cli.ts:1718`) built the weekly session but its **only** output was a
pino line. It never read the experience store and never called `formatLearningStatus`. The routing
evidence rendered **solely** in `scns review weekly` (`cli.ts:3281`) — a command John had to run
himself, so the Monday cron told him nothing about the learning state.

Verified independently before writing code: `formatLearningStatus` (`weekly-format.ts:151`) had
**exactly one** caller (`cli.ts:3281`).

## The fix — extraction + second caller (not a new renderer)

`src/suggest/weekly-report.ts` (NEW) holds the single renderer both callers share:

- `renderLearningStatusSection(input)` — evidence read + render, 3 states (`ok` / `absent` / `failed`)
- `writeWeeklyReviewFile(input)` / `weeklyReviewFilePath(scnsDir, now)`
- `WEEKLY_REPORT_MIN_N = 5`

Callers: `cli.ts` review path (inlined block **deleted**, per Constitution IV) and the cron handler.

### Defect found by the negative control

`countSettledByArm` / `countServedByArm` are deliberately fail-safe — they swallow errors and return
empty maps, because the **live serving path** uses them to pick ε and must never break the answer.
That contract is right there and wrong in the review: a corrupt corpus rendered identically to a
starved learner ("zero settled outcomes"), so the `failed` state was unreachable. Fixed with an
explicit **unguarded** integrity probe before the fail-safe counters:

```ts
s.db.prepare('SELECT COUNT(*) AS n FROM retrieval_experience').get()
```

Required because `new Database(path, { readonly: true, fileMustExist: true })` does **not** throw on
a corrupt file — the throw happens on first query.

## Isolation trap discovered — correction to the handoff's probe rules

`SCNS_HOME` + `BROKER_DB_PATH` are **NOT sufficient** to isolate a broker. `scns start` reads
`-p, --port` with a hardcoded default of `'3456'` (`cli.ts:75`) and **ignores `BROKER_PORT`**. The
first two probe attempts therefore tried to bind the **live** broker's port and died with
`EADDRINUSE: address already in use :::3456`. Any broker probe must pass `--port <free>` explicitly.

### Guard status (FR-035b three claims)

- **(i) live corpus mtime/size unchanged — BROKEN AS STATED.** Live `experience.db` moved
  `size=7008256 mtime=1785664813` (06:00:13) → `size=7053312 mtime=1785681351` (10:35:51).
- **(ii) no probe rows written — HOLDS.** Live `COUNT(*)` is **2056**, identical to the measurement
  taken before any probe. Newest row id 2063 is `2026-08-02 13:12:53Z` — this session's own bootstrap
  prompt, predating all probe work. Zero probe-authored rows.
- **(iii) live broker untouched — PARTIALLY BROKEN.** The live broker PID changed **38887 → 60007**
  (ppid=1, re-parented) during the probe window. Health after: `{"status":"ok","database":"ok"}`.

The mtime/size delta (+45056 B) with **zero row change** is a WAL checkpoint.

**CORRECTED 2026-08-02 (independent judge).** My first stated cause — the live broker restart — is
chronologically impossible: PID 60007 started at **10:40:55**, five minutes AFTER the **10:35:51**
mtime. The EADDRINUSE speculation is also mechanically wrong: a port collision kills the new binder,
never the incumbent listener. The likeliest cause is **my own tooling**: the ~10:35 step that copied
the corpus and produced `COUNT(*)=2056` opened the live database read-write, and SQLite
checkpoint-truncates the WAL on close — which yields exactly a main-file bump with zero row change.
I cannot prove which command did it, so the cause is recorded as **most likely my own read-write open,
undetermined**, rather than attributed elsewhere.

**Lesson for the probe rules:** reading the live corpus requires `sqlite3 -readonly` (or a copy made
before any open), not merely "I only ran SELECTs". A default `sqlite3` open is read-write.
