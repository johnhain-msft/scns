## DP-F5 (MED) — ⚠️ MY TRIAGE WAS HALF WRONG; corrected and resolved 2026-08-02

**What I originally wrote, and why it was wrong.** The evidence I recorded was:

```
$ grep -rn 'routeQueryArm(\|recallSimilarEpisodes(' src/ --include=*.ts
```

That grep is **scoped to `src/`**. The judge's was too, and I reproduced the scope instead of challenging
it. `scripts/` was never searched. Re-running repo-wide:

```
$ grep -rn 'routeQueryArm' --include=*.ts . | grep -v node_modules | grep -v dist
scripts/locomo-judge-harness.ts:134:  import { routeQueryArm } from '../src/memory/arm-router.js'
scripts/locomo-judge-harness.ts:2483:  const d = routeQueryArm(conv.vault.db, it.question, { gazetteer: conv.gaz, lambda })
```

**`routeQueryArm` is LIVE.** It is the C3 "router-as-policy" arm of the arm-frontier judged gate — the very
gate that produces the certified evidence `routing-policy.ts` requires before any arm can be promoted.

("evaluated OFFLINE by the arm-frontier judged gate as a POLICY") and three of us read past it.

**Why nothing caught this.** `scripts/` is outside *every* gate: `tsconfig.json` sets

that broke the harness would have produced a fully green gate. Verified by compiling it explicitly:

## DP-F2 (MED) — fixed 2026-08-02

The `NEGATIVE CONTROL: an ALREADY-ANSWERED question…` case was a no-op: `logRetrievalExperience`'s INSERT
never sets `gate_question` (`experience-store.ts:360-366`), so `UPDATE … SET gate_question = NULL` cleared
a column that was already NULL, making it a byte-for-byte duplicate of the control above it. It now SETS
the question, asserts the guard is genuinely engaged (`expect(followup(...)).toBe(false)` with a non-null
precondition check), then clears it and asserts the reader is freed — so the transition is really observed.
