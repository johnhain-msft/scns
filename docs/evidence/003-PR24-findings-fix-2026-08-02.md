## 1. T096 / FR-041 — the numerator and denominator described different populations

`src/suggest/weekly-review.ts:203-204` (at `2e5b203`):

```js
items: [...chosenPending, ...chosenBackfill],   // numerator: TWO pools
totalPending: input.pending.length,             // denominator: pending only, UNFILTERED
```

Two independent breaks, both in the numerator, and `weekly-format.ts:33` printed
`${packet.items.length} of ${packet.totalPending}`:

- **backfill counted against pending** — with `DEFAULT_BACKFILL_SLOTS = 2` (`:44`), the live 2026-08-02
  header's `5 of 13` was 3 pending + 2 backfill. It escaped notice only because `5 ≤ 13`.
- **`actionable !== false`** — selection filters at `:139`, the denominator did not.

### Red first

```
FAIL  test/unit/suggest/weekly-review.test.ts > selectWeeklyPacket — FR-041 population integrity (T096)
       > sizes the pending queue with the SAME predicate the selection uses
AssertionError: expected 5 to be 3 // Object.is equality
 ❯ test/unit/suggest/weekly-review.test.ts:192:28

 Test Files  2 failed (2)
      Tests  5 failed | 43 passed (48)
```

### The fix

Each pool reports its own numerator against its own denominator, and the pending denominator is now the
population selection actually draws from, with the remainder **disclosed** rather than dropped (T096
forbids "fixing" this by hiding the count):

```ts
selectedPending: chosenPending.length,
selectedBackfill: chosenBackfill.length,
totalPending: actionablePending.length,
nonActionablePending: input.pending.length - actionablePending.length,
```

### Live — the header the Monday cron will render, from the built `dist/`

Isolated `SCNS_HOME`, tmpdir only. 13 actionable pending + 4 non-actionable + 20 unexplained terminal,
`budget: 5`, `backfillSlots: 2` — the shape that produced `5 of 13`:

```
packet: {"items":5,"selectedPending":3,"selectedBackfill":2,"totalPending":13,
         "nonActionablePending":4,"totalUnexplained":20}

Weekly review
─────────────
3 of 13 pending item(s) selected — the ones where your answer would tell me the most.
(4 further pending proposal(s) are marked non-actionable, so they are not eligible for review and sit outside that count.)
2 of 20 past decision(s) with no recorded reason are in this packet too — a separate pool, counted separately. I can only learn from the ones you explain.
```

`3 of 13`, not `5 of 13`. Both other populations are present and labelled.

**NOT done, deliberately:** T110 (DP-F7, LOW) is filed as "fold into T096". It is a *served-side*
rendering gap in `weekly-format.ts:224-232`, not a population-mismatch, and folding it in would have

## 2. T113 / finding A — `existsSync` is not an ENOENT test

Copilot's suppressed comment on `experience-store.ts:622`. Re-derived: `existsSync` returns `false` for
**any** stat error, so a store that is present but unreadable was classified `absent`, which renders:

> There is no experience store at `<path>` — the broker creates it on first retrieval. … This is the
> expected state on a fresh install, **not a failure** — which is why it does not read as "unknown":
> the cause is known and self-resolving.

FR-026 separates `absent` from `failed` *precisely because* `absent` self-resolves and `failed` does not.
The two license opposite next moves.

**The two graders disagreed here and Copilot was right.** The duck examined the same line and cleared it,
considering only the TOCTOU direction (file deleted between check and open, which degrades to `failed`).
It did not consider the opposite direction — present but unreadable.

### Red first

```
FAIL  test/unit/memory/experience-store.test.ts
       > PR#24-A [US1] RED — a PRESENT-but-unreadable store is `failed`, never `absent`
       > classifies a permissions failure as failed, not absent
AssertionError: expected 'absent' to be 'failed' // Object.is equality
      Tests  2 failed | 1 passed | 47 skipped (50)
```

### The fix

`statSync` + errno: `ENOENT ⇒ absent`, everything else ⇒ `failed`. `existsSync` is no longer imported.

### Live, against the built `dist/` — the same repro PR #24 used

```
── PROBE 1: chmod 000 dir, store present inside
   existsSync says      : false
   readSettledByArm     : {"status":"failed","error":"cannot stat …/perm/inner/experience.db: EACCES: permission denied, stat '…/perm/inner/experience.db'"}
   readServedByArm      : {"status":"failed","error":"cannot stat …/perm/inner/experience.db: EACCES: permission denied, stat '…/perm/inner/experience.db'"}
   POSITIVE CONTROL — genuinely missing file:
   readSettledByArm     : {"status":"absent","path":"…/nope.db"}
```

`existsSync` still says `false` — that is the lie, quoted. The read no longer believes it. The positive
control proves the fix did not over-correct: a genuinely missing file is still `absent`.

### The never-throw contract is intact

`cli.ts:1264` (live ε routing) calls `countSettledByArm`, the **fail-safe adapter**, which was not
touched. `readByArm` is not on that path.


here is the proof, from making it required before updating them:

regression cannot be caught by a fixture; a source guard in `wiring-guard.test.ts` pins it instead
(`readonly evidence?:` absent, no `input.evidence ??`).
