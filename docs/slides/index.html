Every session starts with amnesia.

During a session, a coding agent learns real things: which command quietly breaks the build, why that one test is flaky, where the bodies are buried in your repo. The moment the session closes, all of it is gone. The next session re-learns it from zero — on your time and your tokens.

A memory that survives the session.

SCNS is a background service on your machine. It watches coding-agent sessions, keeps what mattered, and hands the relevant part back at the start of the next prompt. Three properties define it:

PERSISTENTMemory outlives the session

Decisions, gotchas, and lessons are stored the moment they're learned and are retrievable weeks later — by meaning, not just by keyword.

PER-REPOSITORYOne brain per repo

Each registered repository gets its own isolated vault. What the agent learns in project A never bleeds into project B.

LOCALNothing leaves your machine

The vault is a SQLite file in your home directory. You can open it, query it, delete it. There is no cloud service to trust and no data to exfiltrate.

The colors in every diagram that follows mean the same thing: gold is a memory, cyan is the live session, rust is what gets filtered out.

How it plugs in.

The agent talks to a local broker over HTTP on loopback only. A supervisor spawns one child broker per repository, each with its own database and its own memory tree.

The extension forwards every hook (session start/end, prompt, tool use, errors) as events, and injects context on each prompt. Everything binds to 127.0.0.1 — nothing is reachable from the network. The broker also exposes an MCP endpoint for other hosts; child ports come from a fixed pool (3500–3599). The same broker layer coordinates multi-agent teams: shared task boards, file claims, and agent-to-agent mail.

One brain per repository.

When a session starts, SCNS resolves the working directory to the deepest registered project root and routes all memory traffic to that project's own child broker. Isolation is physical, not a filter: each child gets its own SCNS_HOME — a separate memory tree and a separate database file.

Why it matters: a user-scoped memory shared across all repos is both noisy (repo A's conventions pollute repo B's answers) and a confidentiality risk (client A's knowledge surfaces in client B's session). A strict mode (SCNS_REQUIRE_PROJECT_BROKER=1) goes further and refuses memory writes entirely if a session didn't resolve to its own project broker.

Writing a memory.

A memory is a markdown file in the vault. On store it is immediately chunked, keyword-indexed, and — before the call returns — embedded as a vector. The contract: if it stored, it's retrievable, right now.

This exact pipeline fixed a real bug: embedding used to be deferred to a half-hourly re-index, so a freshly stored memory was invisible to the next prompt's briefing for up to ~20 minutes — while keyword search still found it, masking the gap. The embed step is now awaited on store. If embedding fails, the memory degrades safely to keyword-searchable and is embedded on the next sweep.

Meaning becomes geometry.

Every chunk of text is run through a small local model (BGE-small-en-v1.5, via ONNX — no API calls) that turns it into 384 numbers: a point in space. Texts that mean similar things land near each other, even with zero words in common.

cos(a, b) = a · b / (‖a‖ ‖b‖) similar meaning → cos near 1 · unrelated → near 0

The model runs in a disposable child process, not the broker: its native runtime pins ~1.3 GB of memory that is never returned. Isolating it keeps the always-on broker at ~180 MB.

Step 1 — cast two nets.

Retrieval starts by finding anchors: the best entry points for the query. Two searches run side by side — exact words and meaning — because each catches what the other misses.

KEYWORD NETFull-text search (FTS5 / BM25)

Catches exact terms: error strings, flag names, file paths. Rank is normalized as 1 / (1 + |rank|).

VECTOR NETNearest neighbors (sqlite-vec)

Catches meaning: "memory leak in the embedder" finds the ONNX-arena note even with no shared words.

score = 0.7 · vector_similarity + 0.3 · keyword_score meaning dominates; exact words still count — top 20 become anchors

Both nets run inside the same SQLite file — FTS5 is built in, and the sqlite-vec extension does the nearest-neighbor search. No separate search server, no vector database service.

Step 2 — follow the graph.

Memory isn't a flat list. Chunks are linked by entity, temporal, and causal edges — so retrieval can walk from an anchor to the memory that explains it, the way you'd follow a thread. (This is the MAGMA paper's Algorithm 1.)

reached & keptpruned branch
hop appeal S = exp( λ₁·φ(edge, intent) + λ₂·sim(node, query) ) path score = parent · γ + S λ₁ = 1.0 λ₂ = 0.5 γ = 0.5 (decay per hop) ≤ 5 hops · ≤ 200 nodes · beam of 8 per step

φ adapts to the question. A "why…" query weights causal edges 5×, a "when…" query boosts temporal edges, a named-thing query boosts entity edges. The walk keeps hopping only while the semantic thread holds — if a neighbor's similarity to the query falls more than 0.15 below the node it came from, that branch is cut.

Step 3 — fuse the evidence.

The keyword net, the vector net, and the graph walk each produce a ranked list. They're combined with Reciprocal Rank Fusion: a chunk that several independent signals rank highly beats a chunk only one signal found.

raw(d) = Σ over sources s of w_s / (60 + rank_s(d)) score(d) = raw(d) / max raw top result = 1.0

RRF only needs each source's ordering, never its raw scores — so a BM25 rank, a vector distance, and a graph-walk score can be combined without inventing a conversion between incompatible scales. The constant 60 is the canonical value from the original RRF paper (Cormack et al. 2009).

Step 4 — fit the budget.

Context space is expensive, so the briefing must fit in ~3,400 tokens. The winning chunks are ordered to read as a narrative, wrapped with provenance, and trimmed by salience — with two guarantees.

The two guarantees: anchors are kept unconditionally (they're the chunks the query matched directly — a pure salience cut would evict them first), and elided runs leave a trace — a brevity code with the skipped chunk ids, so the agent can ask for them if it needs to. Token cost uses a fast ~4-chars-per-token estimate.

What the agent actually sees.

On every prompt — not just session start — a hook fires, sends the prompt to the project's broker, and prepends up to three blocks of context before the model sees it.

Only what's relevant gets in.

Injected noise is worse than no injection. Suggestions and guardrails are scored against the prompt with a deliberately cheap lexical test — this runs on the hot path of every prompt, so it must cost nothing.

score(item) = |item_words ∩ prompt_words| / |item_words| stopwords stripped, words singularized · zero unless ≥ 2 content words match asymmetric on purpose: a short item fully covered by a long prompt scores ~1, where symmetric overlap would unfairly cap it near 0.1

SUGGESTIONSStrict: no match, no injection

Score 0 → dropped entirely. A suggestion is a nudge, not a guardrail — an off-topic nudge is pure noise. Top 3 by score make it in.

GUARDRAILSLenient: a floor of 3, always

"Never hardcode secrets" shares no words with most prompts but still applies. If fewer than 3 rules match lexically, the list is topped up to 3 — a safety rule should not silently retire just because it's phrased generally.

One more balance: pinned rules ("this always applies") skip every quality gate — but they're capped so they can never crowd out rules that actually match today's prompt. Quality is judged first, topicality second: relevance can narrow what quality admitted, never rescue what review rejected.

Why SQLite.

The entire memory of a project is one inspectable file. Full-text search (FTS5) is built in; vector search is the sqlite-vec extension. No search server, no vector-DB service, no connection strings — and nothing to exfiltrate.

Details that matter: triggers keep the FTS index in sync synchronously — a fact is findable the moment it's stored. Embeddings are raw Float32 blobs. WAL journaling keeps reads non-blocking. Expensive LLM-derived causal edges are keyed on stable content hashes so they survive re-chunking; cheap deterministic edges are just rebuilt. Each concern gets its own database file (vault, experience log, broker state, registry) — and each repo's child broker gets its own copy of all of them.

Learning what was worth injecting.

Every briefing is logged as an experience. Human behavior labels it: re-asking the same question means the briefing was waste; answering a clarifying question SCNS asked means accept. A weekly review measures whether the routing between two retrieval tools agrees with those outcomes.

agreement = 0.5 + 0.5 · (accept-rate of the recommended tool − the other tool) stratified by question shape — chance is exactly 0.5 by construction, under any traffic mix cutover bar: 95% lower bound > 0.55 on ≥ 100 rows

Honest status: this is the least finished part of SCNS. The machinery runs end-to-end, but human labels are scarce (~74 of 2,623 logged retrievals), and no learned weight feeds back into live retrieval yet. The metric was designed so that scarcity can't fake a win.
